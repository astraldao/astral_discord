# バックアップ読み上げの使い方

VOICEVOX:ずんだもんで、指定したテキストチャンネルの投稿をVCへ読みます。
普段の読み上げBotが使えないときに `/menu → 読み上げ → このチャンネルで開始` から起動します。

## 使う人の手順

1. 聞きたい通常のVCに参加する。
2. 読み上げたいテキストチャンネルで **`/menu → 読み上げ → このチャンネルで開始`** を実行する。
3. 「投稿を待っています」と表示されたら投稿する。準備中の投稿は読みません。
4. 終わったら **`/menu の「操作」で「読み上げを停止」`** または「読み上げを停止」を押す。

`/menu → 読み上げ` から接続先・待ち件数・直近の開始待ちを確認できます。
「状態を更新」で再取得、「遅延の内訳」で待ち時間を詳しく確認できます。
停止中の画面には「このチャンネルで開始」が表示されます。先にVCへ参加し、読むチャンネルで押してください。

「このチャンネルで開始」を押したチャンネルだけを読み、開始した人の参加中VCに接続します。
サーバーで同時に1組です。別の組へ切り替えるときは、一度停止して新しい場所で開始してください。
テキスト・アナウンス・通常VCのチャットに対応します。スレッドとステージは対象外です。

## 管理者が一度行う設定

1. `/admin → バージョン管理` から最新版を確認し、内容を確認して手動更新する。
2. Discord Developer Portal → 対象アプリ → **Bot → Privileged Gateway Intents → Message Content Intent** を有効にして保存する。承認が必要なアプリでは承認を取得する。
3. `/admin → 運用・管理 → ENV・起動設定` で「バックアップ読み上げ」を選び、`1` を入力して変更内容を確認・保存する。`.env` を編集する必要はありません。
4. 同じ画面の「Botを再起動」から確認・再起動する。再接続後、画面の「稼働中」が `1` になったことを確認する。保存だけではMessage Content Intentは切り替わりません。初回のみ [Quaxlyでの切り替え](RESTART.md#v334以前からの初回切り替え) が必要です。
5. `/admin → 運用・管理 → 動作診断` を開き、バックアップ読み上げの起動設定が **ON**、Python・ランタイム・モデル・辞書が確認できることを確認する。
6. 閲覧できるテキストチャンネルと通常のVCで `/menu → 読み上げ → このチャンネルで開始` → 短い投稿 → `/menu の「操作」で「読み上げを停止」` を試す。

初期状態では機能は無効で、メッセージ本文を取得するIntentも要求しません。
Message Content Intentを有効にする前に起動フラグをONにすると、Discordから接続を拒否される場合があります。
初回のBot導入は [READMEのQuaxly手順](../README.md#quaxlyでgithubから導入更新) を参照してください。
すでにずんだもんの入室告知が使えている環境では、その音声環境を共有します。
未導入の場合は `sh setup-voicevox.sh` で準備します。

### 必要な権限

| 対象 | 必要な条件 |
|---|---|
| 読むチャンネルのBot | チャンネルを見る・メッセージを送信・埋め込みリンク |
| 聞くVCのBot | チャンネルを見る・接続・発言、サーバーミュートされていない |
| 実行者 | 通常のVCに参加し、元のテキストチャンネルを閲覧できる |
| VCの参加者全員 | 元のテキストチャンネルを閲覧できる |

開始した本人か管理者が停止できます。チャンネルが削除された場合や閲覧権限を失った場合も、停止だけは実行できます。状態の閲覧には元のテキストの閲覧権限が必要です。
実行者の移動・退出、元チャンネル・接続先VCの削除、Botの切断・サーバーミュート、必要な権限を確認できない場合は停止します。
入室告知のON/OFFとバックアップ読み上げのON/OFFは独立です。音量は `/admin → 入室・音声 → 音声設定` の値を共用します。
入室告知用の名前・英単語の読み方辞書は、バックアップ本文の置換には使用しません。

## 読む範囲と順番

- 本文をUnicode正規化し、改行などを空白へ整理してから先頭50文字まで読みます。超過時は後ろに「以下略」を付けます。最大53文字、Unicodeコードポイントで数えます。
- 前の文章を最後まで読んでから、投稿順に再生します。途中で割り込みません。
- 読み上げ中に、次の1件だけ音声を先読みします。再生前には参加者と権限を改めて確認します。音量は再生時の設定を使用します。
- 処理中の1件に加え、最大8件が待てます。上限を超えた新しい投稿は読み飛ばし、状態画面に件数を表示します。
- Bot・Webhook・システム投稿、空本文、添付だけの投稿は読みません。開始前・準備中の投稿を後から取得することもありません。
- 停止・障害・再起動で未再生分を破棄します。再開時にまとめて再送しません。
- 本文と生成音声はファイル・ログへ保存せず、外部TTSにも送信しません。生成した音声はDiscordのVCへ送信します。

開始・終了の案内は元チャンネルに表示します。停止の案内には「このチャンネルで開始」があり、VCへ参加してから押すと新しい読み上げを開始します。未再生分を再送することはありません。操作画面は本人だけに表示されます。
古い画面の停止ボタンでは新しく始めた読み上げを止められません。「状態を更新」で現在の状態を開いてください。

## 遅いときの見方

**投稿から300ms以内の読み上げ開始は保証しません。** 文章の順番待ちとDiscordの通信でも遅れます。
最初の準備ではモデルを読み込みます。準備完了後はモデルを常駐させ、先頭の短い音から合成しながら再生します。
v3.29では権限確認とローカル合成を並行し、権限確認が通るまで音を出しません。
v3.34では、前の音声を流している間に次の1投稿だけ合成します。先読みはメモリ内のWAV最大8MiB・256片までで、停止・権限失効時に破棄します。待ち行列8件のうちの1件なので、保持件数は増えません。
文章ごとの一本のストリームに音声をつなぎ、分割のたびに追加されていた末尾無音と再生準備を減らしています。

`/menu → 読み上げ → 遅延の内訳` を見ると、次を区別できます。

| 表示 | 測っている時間 | 確認すること |
|---|---|---|
| 順番待ち | 受信からその文章の処理開始まで | 前の音声と待ち件数。割り込みはせず、投稿順を守ります |
| 権限確認 | 処理開始から閲覧・VC権限の確認完了まで | Discordの応答、参加人数、権限変更 |
| 先頭合成 | 再生する文章の処理開始から先頭音声が届くまで | 先読み済みならほぼ0ms。CPU負荷、VOICEVOXの実行環境も確認 |
| 再生準備 | 権限と先頭音声が揃ってからAudioPlayerのPlayingまで | Bot側のエンコードと処理負荷 |

「次の投稿の先読み」には使用の有無と累計件数を表示します。先読みは順番待ちの間に行うため、先頭合成が0msでも投稿受信からの待ち時間が0msとは限りません。
権限確認と合成は並行するため、内訳を単純に足した値とは一致しません。
「直近の開始待ち」はBotの投稿受信からPlayingまでで、**Discordで実際に聞こえるまでの時間は含みません**。
300ms超過は障害件数ではありません。数値は今回の読み上げセッションだけのもので、停止時にリセットします。

### 手元で計測する

Botを使っていないときに、VOICEVOXがあるBotのルートディレクトリで実行します。

```sh
npm run backup-voice-benchmark
npm run backup-playback-benchmark
npm run backup-queue-benchmark
```

最初は先頭音声の合成のみ、2つ目は実モデルとOpusエンコーダを使ったローカル再生の比較です。3つ目は投稿3件を同時投入し、先読みなし/ありの文章間の待ち時間を比較します。
後者の権限確認には200msの模擬待ちを使い、Discordへは接続しません。実行中はCPUを使います。
`VOICEVOX_BACKUP_THREADS=1..4` で合成スレッドを調整できます。既定は2で、多くすれば速くなるとは限りません。

2026-10-15、CPU割当2コア・ネイティブ2スレッド、日本語3文を各方式2回ずつ、計12回の比較結果です。
順番待ちはありません。先頭の分割は両方式とも2モーラで、文を途中まで省く変更はしていません。

| ローカル計測 | v3.28方式 | v3.29方式 |
|---|---:|---:|
| 再生開始の中央値 | 499ms | 274ms |
| 再生開始の最大値 | 695ms | 283ms |
| 読み終わりまでの中央値 | 4,458ms | 3,681ms |
| 読み終わりまでの最大値 | 9,948ms | 8,350ms |

[計測データ](performance/backup-playback-2026-10-15.json)。小標本の開発環境での結果で、本番Discordの応答時間を示すものではありません。
環境の揺らぎも含むため、今後の実行で同じ数値になる保証はありません。

## 困ったとき

| 症状 | 対応 |
|---|---|
| 「まだ有効になっていません」 | 管理者がIntentと起動フラグを設定し、Botを再起動。動作診断でONを確認 |
| Intent設定後にBotが起動しない | ボタンからの再起動なら直前の設定へ戻して復旧を試みます。Developer Portalの保存状態を確認してから設定し直す。復旧できない場合はQuaxlyで状態を確認 |
| 準備が終わらない | 停止ボタンか `/menu の「操作」で「読み上げを停止」`。動作診断で音声ファイルを確認し、音声環境の導入を確認 |
| 準備完了なのに読まない | 投稿先と「読む場所」が同じか、Bot投稿・添付だけではないかを確認。Intent変更後は再起動が必要 |
| VC参加者の閲覧権限で止まる | 全員が見られるチャンネルで開始する。非公開のテキストを見られない人がいるVCへは流せません |
| 音声・権限・VCの状態を確認できず停止 | Botの接続・発言権限とミュート、CPU負荷を確認し、`/menu → 読み上げ → このチャンネルで開始` で再開。失敗分は自動再生しません |
| 読み飛ばしが増える | 待ち行列が満杯です。投稿を控え、前の読み上げが終わるのを待つ |
| 入室処理が進まない | 音声付き入室と同時には使えません。読み上げを停止してから入室する |
| 更新が始まらない | 読み上げと進行中のゲーム・入室処理を終え、管理者が更新を再実行。自動予約は残りません |
| 古い停止ボタンが使えない | `/menu → 読み上げ` または「状態を更新」から現在の画面を開く |

Discord実機・Quaxlyでの音声と通信時間は開発環境からは検証できていません。導入後は管理者とメンバーで、短い投稿・連続投稿・停止・退出を確認してください。

### 音声接続の障害から再開する

待機中も、音声プレイヤーのエラーと接続終了を監視します。一時的な切断は最大5秒の復旧を待ち、戻らなければ読み上げを停止して接続・合成プロセス・先読み音声を片付けます。読み上げ中や次の再生前に接続異常を検知した場合は、5秒より早く停止する場合があります。
元チャンネルの停止理由を確認し、通常のVCへの参加・Botの発言権限・ミュートを直して「このチャンネルで開始」を押してください。途中の文章や待っていた投稿は自動再送せず、開始後の新しい投稿から読みます。

### v3.34 連続投稿の先読み比較

2026-10-16、CPU割当2コア、実VOICEVOXとOpusで3つの合成用テスト文を同時投入。先読みなし/ありを交互に各2回、文章間の待ちを各4回計測しました。前のAudioPlayerの完了から次のPlayingまでなので、前の文章の読み上げ時間は含みません。Discordの通信は含みません。

| 模擬権限確認 | 先読みなし・中央値 | 先読みあり・中央値 | 最大値の変化 |
|---|---:|---:|---:|
| 50ms | 298ms | 57ms | 331 → 65ms |
| 200ms | 263ms | 207ms | 337 → 213ms |

権限確認が長いほど先読みだけで減らせる待ちには限界があります。最初の投稿の開始待ち、投稿から実際に聞こえるまでの時間、300ms以内の達成率を示す比較ではありません。
記録：[50ms条件](benchmarks/backup-queue-2026-10-16-50ms.json)、[200ms条件](benchmarks/backup-queue-2026-10-16-200ms.json)。再現する場合は `ASTRAL_BENCH_ACCESS_MS=50 npm run backup-queue-benchmark` のように指定します。
