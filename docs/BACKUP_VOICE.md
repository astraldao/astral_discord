# バックアップ読み上げの使い方

VOICEVOX:ずんだもんで、指定したテキストチャンネルの投稿をVCへ読みます。
普段の読み上げBotが使えないときに `/menu → 読み上げ → このチャンネルで開始` から起動します。

## 使う人の手順

1. 聞きたい通常のVCに参加する。
2. 読み上げたいテキストチャンネルで **`/menu → 読み上げ → このチャンネルで開始`** を実行する。
3. 「投稿を待っています」と表示されたら投稿する。準備中の投稿は読みません。
4. 終わったら **`/menu の「操作」で「読み上げを停止」`** または「読み上げを停止」を押す。

`/menu → 読み上げ` から接続先・待ち件数・直近の開始待ちを確認できます。
「状態を更新」で再取得、「遅延の内訳」で待ち時間を詳しく確認できます。
停止中の画面には「このチャンネルで開始」が表示されます。先にVCへ参加し、読むチャンネルで押してください。

「このチャンネルで開始」を押したチャンネルだけを読み、開始した人の参加中VCに接続します。
サーバーで同時に1組です。別の組へ切り替えるときは、一度停止して新しい場所で開始してください。
テキスト・アナウンス・通常VCのチャットに対応します。スレッドとステージは対象外です。

## 一時停止して続ける

`/menu → 読み上げ → 一時停止`。いま合成・再生している文章は最後まで読み、そのあと待機します。VC接続と音声モデルは保持するので、準備をやり直さず **「読み上げを再開」** で続けられます。

一時停止中の投稿も最大8件まで待ち、超えた新しい投稿は読み飛ばします。待っている順番は変えず、先読み済みの1件もそのまま使います。「状態を更新」で待機状態と件数を確認できます。開始した本人か管理者が操作でき、元のテキストの閲覧権限が必要です。接続準備中は一時停止できません。

「読み上げを停止」やVC退出では、接続とモデルを閉じ、待っていた投稿を破棄します。改めて開始しても過去の投稿は読みません。一時停止の時間も「直近の開始待ち」に含みます。

## 管理者が一度行う設定

1. `/admin → バージョン管理` から最新版を確認し、内容を確認して手動更新する。
2. Discord Developer Portal → 対象アプリ → **Bot → Privileged Gateway Intents → Message Content Intent** を有効にして保存する。承認が必要なアプリでは承認を取得する。
3. `/admin → 運用・管理 → ENV・起動設定` で「バックアップ読み上げ」を選び、`1` を入力して変更内容を確認・保存する。`.env` を編集する必要はありません。
4. 同じ画面の「Botを再起動」から確認・再起動する。再接続後、画面の「稼働中」が `1` になったことを確認する。保存だけではMessage Content Intentは切り替わりません。初回のみ [Quaxlyでの切り替え](RESTART.md#v334以前からの初回切り替え) が必要です。
5. `/admin → 運用・管理 → 動作診断` を開き、バックアップ読み上げの起動設定が **ON**、Python・ランタイム・モデル・辞書が確認できることを確認する。
6. 閲覧できるテキストチャンネルと通常のVCで `/menu → 読み上げ → このチャンネルで開始` → 短い投稿 → `/menu の「操作」で「読み上げを停止」` を試す。

初期状態では機能は無効で、メッセージ本文を取得するIntentも要求しません。
Message Content Intentを有効にする前に起動フラグをONにすると、Discordから接続を拒否される場合があります。
初回のBot導入は [READMEのQuaxly手順](../README.md#quaxlyでgithubから導入更新) を参照してください。
すでにずんだもんの入室告知が使えている環境では、その音声環境を共有します。
未導入の場合は `sh setup-voicevox.sh` で準備します。

### 必要な権限

| 対象 | 必要な条件 |
|---|---|
| 読むチャンネルのBot | チャンネルを見る・メッセージを送信・埋め込みリンク |
| 聞くVCのBot | チャンネルを見る・接続・発言、サーバーミュートされていない |
| 実行者 | 通常のVCに参加し、元のテキストチャンネルを閲覧できる |
| VCの参加者全員 | 元のテキストチャンネルを閲覧できる |

開始した本人か管理者が停止できます。チャンネルが削除された場合や閲覧権限を失った場合も、停止だけは実行できます。状態の閲覧には元のテキストの閲覧権限が必要です。
実行者の移動・退出、元チャンネル・接続先VCの削除、Botの切断・サーバーミュート、必要な権限を確認できない場合は停止します。
入室告知のON/OFFとバックアップ読み上げのON/OFFは独立です。音量は `/admin → 入室・音声 → 音声設定` の値を共用します。
入室告知用の名前・英単語の読み方辞書は、バックアップ本文の置換には使用しません。

## 読む範囲と順番

- 本文をUnicode正規化し、改行などを空白へ整理してから先頭50文字まで読みます。超過時は後ろに「以下略」を付けます。最大53文字、Unicodeコードポイントで数えます。
- 前の文章を最後まで読んでから、投稿順に再生します。途中で割り込みません。
- 読み上げ中に、次の1件だけ音声を先読みします。再生前には参加者と権限を改めて確認します。音量は再生時の設定を使用します。
- 処理中の1件に加え、最大8件が待てます。上限を超えた新しい投稿は読み飛ばし、状態画面に件数を表示します。
- Bot・Webhook・システム投稿、空本文、添付だけの投稿は読みません。開始前・準備中の投稿を後から取得することもありません。
- 停止・障害・再起動で未再生分を破棄します。再開時にまとめて再送しません。
- 本文と生成音声はファイル・ログへ保存せず、外部TTSにも送信しません。生成した音声はDiscordのVCへ送信します。

開始・終了の案内は元チャンネルに表示します。停止の案内には「このチャンネルで開始」があり、VCへ参加してから押すと新しい読み上げを開始します。未再生分を再送することはありません。操作画面は本人だけに表示されます。
古い画面の停止・一時停止・再開ボタンでは新しく始めた読み上げを止められません。「状態を更新」で現在の状態を開いてください。

## 遅いときの見方

**投稿から300ms以内の読み上げ開始は保証しません。** 文章の順番待ちとDiscordの通信でも遅れます。
最初の準備ではモデルを読み込みます。準備完了後はモデルを常駐させ、先頭の短い音から合成しながら再生します。
v3.29では権限確認とローカル合成を並行し、権限確認が通るまで音を出しません。
v3.34では、前の音声を流している間に次の1投稿だけ合成します。先読みはメモリ内のWAV最大8MiB・256片までで、停止・権限失効時に破棄します。待ち行列8件のうちの1件なので、保持件数は増えません。
文章ごとの一本のストリームに音声をつなぎ、分割のたびに追加されていた末尾無音と再生準備を減らしています。

`/menu → 読み上げ → 遅延の内訳` を見ると、次を区別できます。

| 表示 | 測っている時間 | 確認すること |
|---|---|---|
| 順番待ち | 受信からその文章の処理開始まで | 前の音声と待ち件数。割り込みはせず、投稿順を守ります |
| 権限確認 | 処理開始から閲覧・VC権限の確認完了まで | Discordの応答、参加人数、権限変更 |
| 先頭合成 | 再生する文章の処理開始から先頭音声が届くまで | 先読み済みならほぼ0ms。CPU負荷、VOICEVOXの実行環境も確認 |
| 再生準備 | 権限と先頭音声が揃ってからAudioPlayerのPlayingまで | Bot側のエンコードと処理負荷 |

「次の投稿の先読み」には使用の有無と累計件数を表示します。先読みは順番待ちの間に行うため、先頭合成が0msでも投稿受信からの待ち時間が0msとは限りません。
権限確認と合成は並行するため、内訳を単純に足した値とは一致しません。
「直近の開始待ち」はBotの投稿受信からPlayingまでで、**Discordで実際に聞こえるまでの時間は含みません**。
300ms超過は障害件数ではありません。数値は今回の読み上げセッションだけのもので、停止時にリセットします。

## 困ったとき

| 症状 | 対応 |
|---|---|
| 「まだ有効になっていません」 | 管理者がIntentと起動フラグを設定し、Botを再起動。動作診断でONを確認 |
| Intent設定後にBotが起動しない | ボタンからの再起動なら直前の設定へ戻して復旧を試みます。Developer Portalの保存状態を確認してから設定し直す。復旧できない場合はQuaxlyで状態を確認 |
| 準備が終わらない | 停止ボタンか `/menu の「操作」で「読み上げを停止」`。動作診断で音声ファイルを確認し、音声環境の導入を確認 |
| 一時停止のあと読まない | `/menu → 読み上げ` で「読み上げを再開」。状態と待ち件数を確認 |
| 準備完了なのに読まない | 投稿先と「読む場所」が同じか、Bot投稿・添付だけではないかを確認。Intent変更後は再起動が必要 |
| VC参加者の閲覧権限で止まる | 全員が見られるチャンネルで開始する。非公開のテキストを見られない人がいるVCへは流せません |
| 音声・権限・VCの状態を確認できず停止 | Botの接続・発言権限とミュート、CPU負荷を確認し、`/menu → 読み上げ → このチャンネルで開始` で再開。失敗分は自動再生しません |
| 投稿するとBotがVCから抜ける | `/menu → 読み上げ` を開き、直前の停止理由を確認。v3.35.1以降は理由コードと対処を表示します |
| 読み飛ばしが増える | 待ち行列が満杯です。投稿を控え、前の読み上げが終わるのを待つ |
| 入室処理が進まない | 音声付き入室と同時には使えません。読み上げを停止してから入室する |
| 更新が始まらない | 読み上げと進行中のゲーム・入室処理を終え、管理者が更新を再実行。自動予約は残りません |
| 古い停止ボタンが使えない | `/menu → 読み上げ` または「状態を更新」から現在の画面を開く |

Discord実機・Quaxlyでの音声と通信時間は開発環境からは検証できていません。導入後は管理者とメンバーで、短い投稿・連続投稿・停止・退出を確認してください。

### 投稿後にVCから抜ける場合

`/admin` が使える場合は、Bot全体ではなく読み上げセッションだけが停止した可能性があります。v3.35.1以降は、開始時の投稿と `/menu → 読み上げ` の停止中画面に理由を表示します。コンソールにも `読み上げ停止: 理由コード` を出します。本文・音声・生の例外・ファイルパスは出力しません。

| 理由コード | 確認すること |
|---|---|
| `ACCESS` | Botのテキスト閲覧・VC接続・発言権限。Discordへの確認が失敗した場合も含む |
| `AUDIENCE` | VC参加者全員が読み上げ元のテキストを閲覧できるか |
| `OWNER` | 読み上げを開始した人が元のVCに参加しているか |
| `CONNECTION` | Botの切断・サーバーミュート・音声ネットワーク。短い切断は最大5秒の復旧待ち |
| `SYNTHESIS` | 動作診断のPython・VOICEVOXモデル・辞書と音声環境 |
| `SYNTHESIS_START_TIMEOUT` | 先頭音声が30秒届かない。QuaxlyのCPU負荷・割当と合成スレッド数 |
| `SYNTHESIS_TIMEOUT` | 分割合成の音声が15秒間届かない。CPU負荷と合成スレッド数 |
| `SYNTHESIS_LIMIT` | 進捗があっても文章全体の合成が60秒を超えた |
| `SYNTHESIS_EXIT` | 音声プロセスが終了。Quaxlyのメモリ不足・CPU・音声環境 |
| `SYNTHESIS_PROTOCOL` | 音声データの形式や順番を確認できない。実行版とVOICEVOX環境 |
| `PLAYBACK` | 再生・エンコード・CPU負荷。音声データが20秒途切れた場合や全体60秒の超過も含む |

理由はメモリ内だけで保持し、新しい読み上げの準備完了かBot再起動で消えます。表示には本文・元チャンネル名・参加者名を含めません。失敗した文章や待ち行列は破棄し、自動再送しません。

コンソールの `操作: 10062` はDiscordの操作応答の期限切れです。読み上げ停止の理由コードとは別なので、それだけで音声停止の原因は分かりません。管理メニュー・更新・再起動の通常操作は、権限の再取得より前に応答を保留するようにしました。すでに失効した操作は再送せず、新しい画面から開き直してください。

### 音声接続の障害から再開する

待機中も、音声プレイヤーのエラーと接続終了を監視します。一時的な切断は最大5秒の復旧を待ち、戻らなければ読み上げを停止して接続・合成プロセス・先読み音声を片付けます。読み上げ中や次の再生前に接続異常を検知した場合は、5秒より早く停止する場合があります。
元チャンネルの停止理由を確認し、通常のVCへの参加・Botの発言権限・ミュートを直して「このチャンネルで開始」を押してください。途中の文章や待っていた投稿は自動再送せず、開始後の新しい投稿から読みます。

### v3.34 連続投稿の先読み比較

2026-10-16、CPU割当2コア、実VOICEVOXとOpusで3つの合成用テスト文を同時投入。先読みなし/ありを交互に各2回、文章間の待ちを各4回計測しました。前のAudioPlayerの完了から次のPlayingまでなので、前の文章の読み上げ時間は含みません。Discordの通信は含みません。

| 模擬権限確認 | 先読みなし・中央値 | 先読みあり・中央値 | 最大値の変化 |
|---|---:|---:|---:|
| 50ms | 298ms | 57ms | 331 → 65ms |
| 200ms | 263ms | 207ms | 337 → 213ms |

権限確認が長いほど先読みだけで減らせる待ちには限界があります。最初の投稿の開始待ち、投稿から実際に聞こえるまでの時間、300ms以内の達成率を示す比較ではありません。
記録：[50ms条件](benchmarks/backup-queue-2026-10-16-50ms.json)、[200ms条件](benchmarks/backup-queue-2026-10-16-200ms.json)。再現する場合は `ASTRAL_BENCH_ACCESS_MS=50 npm run backup-queue-benchmark` のように指定します。

### v3.35.2 合成が進んでいても15秒で停止していた場合

v3.35.1までの `SYNTHESIS_TIMEOUT` は、最初の音声が届かない場合も、音声を生成し続けている場合も、1文章全体を15秒で打ち切っていました。まず `/admin → バージョン管理` からv3.35.2以降に更新してください。

現在は先頭音声まで最大30秒、以後は有効なWAVの分割データが届くたびに15秒の待機期限を更新します。文章全体の合成は60秒までです。途中までの不完全なデータや不正なWAVでは期限を延長しません。再生側は約20秒まで音声データを待ち、合成側の15秒の監視より先に3秒で終了してしまう問題も修正しました。通常時に待ち時間を追加する処理はありません。

`SYNTHESIS_START_TIMEOUT` が続く場合は、最初の分割合成にも30秒以上かかっています。QuaxlyのCPU割当・使用率を確認してください。`/admin → 運用・管理 → ENV・起動設定` の合成スレッド数を `1` にして保存し、「Botを再起動」から反映する方法もあります。CPU制限下ではスレッドを増やすほど速くなるとは限りません。

停止ボタンは合成待ちでも利用でき、Pythonプロセスと待機タイマーを閉じます。失敗した文章と待ち行列は自動再送しません。タイムアウトの変更は読み上げ開始300msの保証を意味しません。

### 実機でスペックと合成速度を測る

v3.36以降は `/admin → 運用・管理 → 動作診断 → 処理速度を測る → 測定を開始` から実測できます。CPU・メモリ割当と、先頭音声・合成完了・Opus変換・CPU制限発生状況を確認します。固定文だけを使い、VCには音声を送信しません。[測定項目と切り分け手順](DIAGNOSTICS.md) を参照してください。

停止ログには稼働版と「文章解析/分割合成/音声受信」、完了片数・対象片数・経過時間などの固定項目を追加しています。これらの進捗通知だけで合成の期限を延長することはありません。準備完了の前には、本番と同じ分割合成で作ったWAVをNode側でも検証します。

## v3.37 1コアの割当で使う場合

合成スレッド数は保存済みの上限とCPU割当から選びます。1コアなら保存値が3でも実行1に抑えます。設定の保存し直しは不要で、動作診断で実行数を確認できます。CPUを共有しているホストでは、同じ割当でも速度が変わります。

Opusの初期化は接続の準備に含め、接続中は同じ変換環境を再利用します。Bot本体で同期的に初期化・変換する処理を専用ワーカーへ移しました。接続完了・音声モデル・Opusの準備が揃ってから新しい投稿を受け付けます。開始直後の待ち時間と、投稿ごとの読み上げ待ちを分けて確認してください。音声の形式・音量と50文字＋「以下略」、投稿順の再生は同じです。

## v3.38 文章全体の情報を共有する合成

対応する音声環境では、文章全体の発音・アクセント・長さを一度だけ計算し、その結果から先頭の約128ms分、次に最大512ms分、以後は最大2.048秒分の音声を順に取り出します。短い句ごとに同じ計算を繰り返す回数を減らし、文章全体の文脈を保ちます。読み上げの速度・音量・声は従来と同じです。

1回の生成が遅い環境では、直前の処理速度から次の分割を小さくします。有効なWAVが15秒間届かなければ停止する監視、先頭30秒・文章全体60秒の上限は従来どおりです。進捗通知だけでは期限を延ばしません。本文50文字＋「以下略」、投稿順、次の1投稿だけの先読みも維持します。

この経路はVOICEVOX Core 0.17.0の非公開APIを限定して使用します。バージョン・メソッド・固定文の生成結果を準備時に確認し、利用できない環境では公開APIへ切り替えます。公開APIでは先頭2モーラ、以後は複数の短い句を最大12モーラにまとめます。投稿の途中で方式を切り替えて重複再生することはありません。診断結果の「合成方式」で使用中の方式を確認できます。

更新は `/admin → バージョン管理` から実行します。ENVの変更・音声環境の再導入は不要です。更新後、読み上げを終了した状態で動作診断の処理速度を測り直してください。[開発環境の比較記録](performance/voice-shared-render-2026-10-17.json) と [実モデル・Opus・3投稿再生の記録](performance/voice-shared-render-playback-2026-10-17.json) は、Discord通信・Quaxlyの共有負荷・589MiBのメモリ制限を含みません。300ms以内の実際の読み上げ開始を保証するものではありません。

## v3.38.1 経過時間とCPU実行時間を分ける

処理速度の診断に、モデル準備・先頭音声・合成と、Opus初期化・変換のCPU実行時間を追加しました。経過時間が長いときに、実際の計算時間と、実行待ちや入出力などを切り分ける材料になります。通常の読み上げを速くする変更ではなく、測定する固定文や合成方式・文字数・待機期限も同じです。更新後、読み上げを終了して `/admin → 運用・管理 → 動作診断 → 処理速度を測る` から測定してください。[CPU時間の範囲と読み方](DIAGNOSTICS.md#v3381以降のcpu実行時間) を参照してください。

## v3.38.2 準備完了前の停止を調べる

`SYNTHESIS_WARMUP_TIMEOUT` では、90秒以内に音声の準備を完了できていません。v3.38.2以降は準備中にも到達箇所を記録し、タイムアウト後も「準備箇所」「この段階の経過」「準備CPUの最終記録」を確認できます。以前の版では準備完了前のCPU記録がなく、今回のような0片での停止を絞り込めませんでした。

更新は `/admin → バージョン管理` から行い、追加ENVは不要です。準備時間の上限や合成方式を変える更新ではありません。詳細は [準備タイムアウトの読み方](DIAGNOSTICS.md#v3382以降の準備タイムアウト) を参照してください。

## v3.39 合成の重複計算を減らす

特徴量を共有する方式では、音声の分割ごとに前後14フレームずつを余分に計算します。v3.39は2つ目の分割を調整し、最後の短い断片だけを生成する呼出しを減らします。先頭12フレームと、それ以後の最大192フレーム・10秒を目安に縮める処理は維持します。

最初の短い音声が終わってからの途切れが従来より長くなると予測される場合、2つ目は従来の短い分割を使います。後半の処理も従来と同じです。文章の長さと測定時の速度により、従来と同じ分割数になる場合があります。途切れの予測は直前のネイティブ処理時間による目安で、ホストの負荷変動まで保証するものではありません。

声・モデル・発音設定・音量・先頭音声の長さは変えません。短い先頭を先に返すだけの高速化や、モデルの軽量版への交換はしていません。本文50文字＋「以下略」、投稿順・次の1投稿だけの先読み、容量・待機の全上限も同じです。更新は `/admin → バージョン管理` から行い、ENV変更や音声環境の再導入は不要です。

[実モデルでの比較](performance/voice-render-workload-2026-10-18.json)・[実OpusとAudioPlayerの比較](performance/voice-render-playback-2026-10-18.json)・[3投稿のFIFOと先読み](performance/voice-render-fifo-2026-10-18.json) は開発環境の測定です。Discordの通信・実機の共有負荷・589MiB上限は含みません。先頭300msの達成を示す変更ではありません。

### v3.41.5 の受信処理

モデルからの音声断片を容量制限付きの領域に取り込み、到着のたびに受信済み全体をコピーする処理を除去しました。完全な音声がそろってから順番に渡し、停止時には未完成の音声を破棄します。合成モデル・読み上げ上限・タイムアウト・次の1件だけの先行準備は同じです。
