# スペックと音声の処理速度を診断する

管理者が `/admin → 運用・管理 → 動作診断` を開くと、稼働版・音声環境・権限に加え、CPU上限・CPU並列度・メモリ使用量/上限を確認できます。診断画面を開くだけでは合成テストを開始しません。

## 処理速度を測る

1. 読み上げとVC入室を終了する。
2. 動作診断の **「処理速度を測る」** を押す。
3. 説明を確認して **「測定を開始」** を押す。
4. 準備・合成・Opus変換の順に測定する。「状態を更新」で現在の段階を確認でき、「測定を中断」で中止できる。
5. 完了すると同じ非公開画面に結果を表示する。別画面へ移動した場合は上書きせず、測定画面を開き直すと結果を確認できる。

固定文「こんにちは。音声の処理速度を確認しています。」を使い、チャンネルの投稿は取得しません。VCへの接続・音声送信・音声ファイルの保存は行いません。バックアップ読み上げの起動フラグがOFFでも、音声環境があれば測定できます。

| 測定項目 | 意味 |
|---|---|
| モデル準備 | 新しいPythonプロセスを起動し、ずんだもんのモデルと分割合成を準備するまで |
| 先頭音声まで | 準備完了後に固定文を渡してから、最初のWAVを受信するまで |
| 合成完了 | 固定文の合成要求から、全分割データと完了通知を受信するまで |
| 音声の長さ・片数 | 生成したPCMの総時間と分割データ数 |
| 最長の分割待ち | 2片目以降で、前の音声データから次の音声データが届くまでの最大時間 |
| Opus変換 | 最初の分割音声・最大1秒分を変換する時間。v3.37以降は専用ワーカーの初期化と変換の内訳も表示 |
| 実時間比 | 合成完了時間 ÷ 生成した音声の長さ。1未満なら再生時間より速く合成 |
| CPU制限発生 | 測定前後のcgroupの制限発生期間数 ÷ 実行期間数。CPU速度の割合ではない |

測定は1回ずつ実行し、終了・失敗・中断の後は30秒間隔を設けます。モデル準備90秒、先頭音声30秒、分割音声の進捗待ち15秒、合成全体60秒、Opus初期化30秒＋準備後の変換5秒（合計35秒）を上限とします。音声処理との同時実行を防ぎ、測定中の更新・再起動は見送ります。

モデル準備は新しいPythonプロセスで行いますが、OSのファイルキャッシュは削除しません。結果はその時点の負荷を含む1回の実測です。Discordの権限確認、通信、VCで聞こえるまでの時間は含まず、300ms以内の読み上げを保証する測定ではありません。

## スペックの見方

CPU上限は確認できるcgroupの割当をコア換算で表示します。たとえば0.25コアは、CPU時間の上限が1コアの約25%である設定です。CPU並列度はプロセスから利用可能に見える論理CPU数で、専用コアの数ではありません。上限を読み取れない場合は「未確認」と表示し、確認できるcgroupに上限がない場合は「未設定」と表示します。ホスティングの上位の制限やCPUの共有状況まで判定できるとは限りません。

メモリはコンテナで確認できる使用量と上限です。上限が不明でOSの値を使う場合は参考値と表示します。測定結果の使用量は終了時点の値で、測定中のピークではありません。CPU制限のカウンターもコンテナ全体の値なので、他の処理の影響を含みます。

## 止まった箇所を確認する

失敗時にも、受信できた片数・先頭音声までの時間など、そこまでの結果を表示します。停止理由には「モデル準備」「文章解析」「分割合成」「音声受信」と対象の片数、経過時間、最終音声からの時間、実際のスレッド数を表示します。

通常の読み上げでの直前の停止理由も動作診断に表示します。コンソールには稼働版と、同じ固定項目の数値を記録します。投稿本文・生成音声・トークン・生の例外・ファイルパスは記録しません。

| 結果 | 次に確認すること |
|---|---|
| モデル準備で失敗 | Python・音声ランタイム・モデル・辞書と、準備中のCPU/メモリ |
| 固定文でも分割合成が止まる | 対象の片数・CPU上限・制限発生状況・使用スレッド数 |
| 実時間比が1以上 | CPUの割当と負荷。スレッド数1の測定と比較する方法もある |
| 合成は成功しOpusで失敗 | 音声エンコーダの導入状態とNode側の処理負荷 |
| 固定文は成功し投稿時だけ停止 | 読み上げの直前の停止理由と、固定文の測定結果を比較する |

スレッド数を試す場合は `/admin → 運用・管理 → ENV・起動設定` から変更・保存し、「Botを再起動」で反映します。診断自体は設定を自動で変更しません。

結果はメモリ内に直近1件だけ保持し、管理者が再表示できます。再起動で消えます。画面の本人・元チャンネル・10分期限・世代・現在の管理者/閲覧権限を検証し、測定の中断は開始した画面から行います。

## 画面が更新されない・中断と表示された場合

v3.36.1以降は、Discordへの進捗返信や権限取得が一時的に失敗しても、開始済みの固定文の測定を中断しません。「動作診断 → 処理速度を測る」から開き直すと、測定中の状態または直近の結果を再表示できます。結果を表示するときには現在の管理者権限と閲覧権限を確認します。測定にはこれまでと同じ時間上限があり、無期限には続きません。

「操作により測定を中断しました」は開始した画面の中断操作、「Bot停止により測定を中断しました」はBotの停止処理による中断です。タイムアウトは失敗理由コードを表示します。Botの再起動後は結果が消えるため、過去の画面には更新前の表示が残る場合があります。

v3.36.0では、開始後の画面更新が失敗すると測定自体も中断してしまう不具合がありました。操作せずに「中断」となった場合は、まず管理者のバージョン管理からv3.36.1以降へ更新して測定し直してください。

## v3.37以降のスレッドと音声変換

ENV画面の合成スレッド数は「上限」です。保存値を読み、利用可能なCPU並列度とcgroupで確認できるCPU割当の整数部分までに制限します。最小は1です。設定上限3・CPU1コアなら実行1と表示します。保存済み設定や `.env` を変更する処理ではありません。CPU上限を確認できない場合は利用可能な並列度を使います。ホストの上位制限や他利用者との競合まで検出できるとは限りません。

Opusの総時間には、診断のために新しく起動する変換ワーカーの初期化を含みます。「初期化」と「変換」の内訳を区別してください。通常のバックアップ読み上げは接続準備時に初期化し、同じVC接続中は変換環境を再利用します。接続の準備時間を、各投稿の読み上げ開始時間に足し込む必要はありません。
