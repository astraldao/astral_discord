# カレンダーの比較調査と改善方針

調査日: 2026-10-24。対象: v5.7.0 / `cbd7d02b8f82b206cbb78b6a645e40e256871fc0`。

結論は、装飾や表示モードを増やす前に、**縮小時の読みやすさ・文字の濃さ・画像で省略した予定への到達**を改善すること。既存の月の一覧・週間・今日から30日を活かし、日程調整の機能は追加しない。

これは公式資料と実装に基づく比較研究であり、各サービスの実機操作監査ではない。以下の現状の数値は調査対象のv5.7.0に基づく。実装済みの範囲は次の節に記録する。

## 実装への反映（v5.8.0）

- 補助文字を`#5a626a`へ変更。予定帯6色を含む使用背景に対して4.5:1以上を確保し、実際に描画したPNGの文字と背景でも検証する。前後の月の淡い背景と月表記を保つ。
- 月画像の上で「表示を切り替える → 月の一覧」を案内し、既存の一覧で予定名と時刻を文字で読めることを明示する。表示モード・ボタンは増やさない。
- 当月に隠れた予定帯がある場合、既存の日付選択の入口を「省略のある日から探す」に切り替える。実際の画像と同じ配置計算で日付と残り件数を求め、その日を選ぶと文字の一覧を開く。通常の日付選択や元の月にも戻れる。

週ごとの情報量や高さ、長い予定名の補足件数の変更は引き続き比較候補。本番のDiscord端末での表示確認は未実施。

## 調査した資料

以下は実際に取得して本文を確認した公式資料。閲覧時点の説明を記録し、他サービスの仕様とBotへの提案を分けた。

| 対象 | 公式資料で確認できたこと | Botに取り入れる考え方 |
|---|---|---|
| Google Calendar [PC][google-pc] / [iPhone][google-ios] | PCは日・週・月・年・スケジュールなどを切り替え、選んだ表示を維持。iPhoneは日付選択・今日への移動・スケジュール表示を案内 | 月の全体像と、文字で読む一覧の役割を明確にする。既存の「表示を切り替える」を活かす |
| Apple Calendar [iPhoneガイド][apple] | 月表示をCompact（1日ごとの指標）・Stacked（予定ごとの指標）・Details（予定名）に切り替え可能。日別と全体の一覧もある | 小さい月枠に全情報を詰め込む必要はない。既存の月の一覧を詳細表示として活かし、新しい密度設定はまず増やさない |
| TimeTree [共有カレンダー][timetree-app] / [Web][timetree-web] | 今日への復帰、月指定、表示切替、検索を用意。終日は濃い背景、時刻付きは淡い背景で区別 | 今日・表示中の日付・終日/時刻付きの意味を分かりやすくする。色だけで意味を伝えない |
| TimeTree [Webの表示件数][timetree-density] | ブラウザーを縮小すると月表示の件数や週表示の時間範囲を増やせると説明 | 情報量と文字サイズには交換条件がある。この方法をDiscordの添付画像にそのまま使うことはできない |
| Fantastical [Macの表示][fantastical] | 大きなカレンダーのサイドバーに、その表示範囲の予定要約を表示。小窓にも予定一覧・入力・検索をまとめる | 俯瞰から詳細へ進める組み合わせを参考にする。Discordでは横並び固定サイドバーではなく、既存の文字一覧と選択欄へ置き換える |
| FullCalendar [週数][fc-weeks] / [前後の月][fc-context] | 固定6週、または月に応じた4〜6週を選べる。前後の月の日付表示は別の設定 | 「必ず6週」が唯一の正解ではない。Botの翌月予告を維持し、余白と縦の長さを実例で比較する |
| FullCalendar [省略された予定][fc-overflow] | 日の表示上限を超えた予定は、`+more`からポップオーバーで開ける | 残り件数には詳細への導線が必要。Botの画像内の`+N件`は押せないため、日付選択へつなぐ |
| W3C [文字のコントラスト][wcag-contrast] / [色の使用][wcag-color] | 通常文字は4.5:1、大きい文字は3:1が目安。色だけを情報の唯一の手掛かりにしない | 当月・翌月は背景と月表記でも区別し、薄字の予定名自体は読める濃さを確保する |

TimeTreeの共有カレンダー公式図も確認した。今日の丸印、選択した日の背景、終日と時刻付きの異なる帯、下部の主要操作が示されている。ただし、資料に載る画面の余白やボタン数が、このBotにも適するとは限らない。

## 現状で維持すること

- 土曜で終わる月にも翌週を追加する5〜6週の表示。前後の月の予定と、月をまたぐ帯の同じ段への配置。
- 当月件数と前後の月の予定を分ける集計。ほかの予定表を混ぜない公開範囲。
- 日付順に文字で読む月の一覧、週間、今日から30日、日付選択、検索、予定の詳細。
- 月移動とページ移動を区別した配置。主要ボタンは1行3個以内、全体はDiscordの5行以内。
- 日程調整は候補への回答を集め、予定表は確定予定を扱う役割分担。

## 実装と描画から分かった課題

実装は [calendar-image.js](../src/calendar-image.js) と [schedule-ui.js](../src/schedule-ui.js) を確認。架空データで10月・11月・時刻付き・200件の混雑例を再描画して画像を確認した。本番の予定や個人データは使っていない。

### 1. スマホで縮小すると文字が小さい

画像は幅840px。通常文字20px、補助文字や一部の短縮タイトル16pxを使う。縦横比を保った表示の換算は次のとおり。

| 画像の表示幅 | 20pxの文字 | 16pxの文字 |
|---|---:|---:|
| 320px | 約7.62px | 約6.10px |
| 375px | 約8.93px | 約7.14px |
| 420px | 約10.00px | 約8.00px |

計算は`文字サイズ × 表示幅 ÷ 840`。これは指定幅への幾何学的な換算であり、Discordが実際にこの幅で表示することを確認した値ではない。端末・添付の表示方法・拡大操作で変わる。

**提案:** 画像は月の位置関係の把握に使い、重要な予定名と時刻は既存の文字一覧で読めるようにする。画像のタイトルをさらに小さくして件数を増やす変更は避ける。既存の「月の一覧」を選ぶと何が得られるか、表示選択の説明を改善する。新しい「スマホ専用カレンダー」は作らない。

### 2. 薄字が読みづらい

補助文字色`#767d84`の理論上のコントラスト比を、実装の背景色から計算した。

| 使われる背景 | 比率 |
|---|---:|
| 白 `#ffffff` | 約4.17:1 |
| 前後の月の背景 `#f8f9fb` | 約3.96:1 |
| 前後の月の予定帯6色 | 約3.78〜3.97:1 |
| 当月の予定帯6色 | 約3.26〜3.66:1 |

補助文字は見出し・曜日・前後の月の文字・時刻などに使われる。**当月の通常の予定名は別の濃い文字色**であり、この測定を全タイトルの値と取り違えないこと。比率は元のRGB色の値で、縮小後や輪郭のアンチエイリアス部分の測定ではない。

**提案:** 補助文字も実際に使う全背景で4.5:1以上となる色へ変更する。前後の月は淡い背景と`11/1`のような月表記で区別する。「翌月を薄字にする」という意図を保ちつつ、文字そのものを読みづらくしない。これだけでアクセシビリティ全体への適合を主張しない。

### 3. 省略された予定から詳細へ進む操作が分かりづらい

月表示では最大3段の予定帯と`+N件`を描くが、画像内の数字は押せない。既存の予定選択欄には日時も入るがページ単位。日付選択は補助操作の中にあり、画像の特定の日と選択欄の予定の対応を利用者が探す必要がある。

**提案:** 予定が隠れた場合に「○日の残りを確認」と日付選択への進み方を示す。既存の日付選択を再利用し、その日の予定を開ける形にする。全日分のボタンや、別の検索機能は追加しない。前後の月だけの予定は、今と同じく月を移動してから開き、選択欄へ無関係な月を混ぜない。

### 4. 週ごとに情報量が変わる

現在は混んだ週をコンパクトにし、空いている週は予定名の折り返しや時刻を表示する。空白を減らせる一方、同じ月でも「時刻がある帯」と「表示されない帯」が混在する。見えない時刻を「終日」と誤解しない説明が必要。

**提案:** 月表示で常に伝える情報を先に決める。候補は「日付と予定名を優先し、時刻の全件確認は一覧」。終日と時刻付きの区別には文字や形も使う。固定の週高にするかは、短い名前・長い名前・混雑月で比較してから決める。他サービスに合わせて一律6週や固定高へ戻すことはしない。

### 5. 長い予定名の補足で画像が伸びる

架空データの再描画結果。いずれも幅840px。高さは予定の長さ・数・分布で変わるため、実利用の平均値ではない。

| 検証例 | 高さ | PNGの容量 |
|---|---:|---:|
| 10月・月末と翌月の予定 | 800px | 23,500 bytes |
| 11月・少ない予定 | 564px | 15,663 bytes |
| 時刻付きと長い名前 | 754px | 20,349 bytes |
| 200件・長い名前 | 1,584px | 51,047 bytes |

画像下の「省略した予定名」は最大8件。ここまで伸びると下の操作欄を確認するスクロール量が増える可能性がある。実際のDiscord上での量は未計測。

**提案:** 補足一覧をさらに増やすことは避け、文字一覧への案内を強める。補足を短くする案は「同じ接頭辞の予定名を取り違えないか」を確認してから採用する。情報を消して画像高だけを減らす評価にはしない。

## 改善の優先順位

| 優先 | 変更候補 | 確認すること |
|---|---|---|
| P1 | 補助文字色を濃くする | 実際に使う背景のすべてで4.5:1以上。前後の月・今日・選択日の区別を保つ |
| P1 | 画像と既存の文字一覧の説明を揃える | 月の全体像から完全な予定名・時刻へ迷わず移れる。表示モードや主要ボタンを増やさない |
| P2 | 隠れた予定の日付へ進む導線 | 既存の日付選択を再利用。複数ページ・空の日・前後の月でも意図した範囲を開く |
| P2 | 月表示の情報量を統一する案を比較 | 時刻が省略された予定と終日を取り違えない。横につながる複数日の予定を保つ |
| P3 | 長い名前の補足と週高を調整する | 画像の長さだけでなく、同名に近い予定の識別と操作欄への到達も比較する |

次の試作では、現行・文字を濃くした案・情報量を揃えた案を同じ架空データで比較する。比較タスクは「今日を見つける」「来月最初の予定を探す」「隠れた4件目を開く」「長い名前2件を見分ける」「一覧から月へ戻る」。主観での見栄えだけで決めない。

受け入れ確認には、予定0件・1件・200件、日付に4件以上、月末が土曜、2月、年越し、月をまたぐ複数日の予定、同じ接頭辞の長い名前、色を変えた予定、管理用/閲覧用を含める。PCとスマホで文字・スクロール・選択欄・戻る操作を確認する。本作業では本番Discordへの接続がないため、この実機確認は未実施。

## 仕様を変える際の境界

- Discordの画像はクリック可能な日付セルではない。ネイティブの選択欄を使い、CSSによるPC/スマホの別配置ができるようには説明しない。
- 一覧・検索・月単位のICS・当月件数の意味を変えない。前後の月を見せても別の予定表は表示しない。
- 操作者・チャンネル・閲覧/編集権限・操作期限・最新の保存内容を再確認する既存の仕組みを維持する。
- 日程調整への回答・招待・出欠・自動通知を、見た目の改善に混ぜて追加しない。
- 外部サービスやFullCalendarの導入、外部API、追加依存関係は、この調査の採用条件ではない。
- Botへの反映は実装と検証後、従来どおり管理者の手動更新で行う。

## 数値の再確認

文字の換算は`20 * 375 / 840`と`16 * 375 / 840`などで再計算できる。色の比率はsRGBを線形化した相対輝度から算出した。次の例は白背景の約4.17:1を再現する。

```js
const luminance = rgb => rgb.map(v => v / 255)
  .map(v => v <= 0.04045 ? v / 12.92 : ((v + 0.055) / 1.055) ** 2.4)
  .reduce((sum, v, i) => sum + v * [0.2126, 0.7152, 0.0722][i], 0);
const a = luminance([118, 125, 132]);
const b = luminance([255, 255, 255]);
console.log((Math.max(a, b) + 0.05) / (Math.min(a, b) + 0.05));
```
